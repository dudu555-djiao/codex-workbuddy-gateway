# 桌面桥接失败复盘

## 2026-10-08 v0.2.0 简单文件实测

用户授权由 Codex 自选简单任务，并明确不做视频。本轮任务为让 WorkBuddy 新建一个包含唯一测试标记的三条 Markdown 清单，再在同一个会话修改第三条。

实测结果：

1. 打开本机 WorkBuddy 5.7.6。桌面登录正常，通过 Computer Use 在新会话发送一次仅要求回复“准备好了”的准备消息，WorkBuddy 正常完成回复；此步骤仅用于创建会话，不算桥接派工。
2. 只读检查确认该会话存在于 WorkBuddy 原生历史，具有真实工作目录。回复结束后，运行时注册目录只有 `prewarm` 项，其中是 Unix 控制 socket，没有本实现要求的 `interactive` HTTP ACP endpoint。
3. 通过已加载的 v0.2.0 `workbuddy_send_task` 发送真实清单任务，返回 `queued`。随后 `workbuddy_wait` 得到 `blocked`，错误为 `The bound WorkBuddy desktop conversation is offline`。
4. 独立检查指定目标文件，文件不存在；没有实际清单成果，未进入返工，未记录验收通过。Codex 没有代写该文件。

因此当前问题已经收窄到真实桌面运行时发现和会话恢复；不能仅凭界面正常、原生历史存在或模拟测试通过，就声称桥接可用。注册目录条件把无法发现 ACP 运行时呈现为“会话离线”，不代表桌面 WorkBuddy 本身不能执行任务。

下一步需找到并验证当前 macOS 桌面版本实际使用的会话连接/恢复通道，或明确实现并标注桌面自动化路径。不能直接将 `prewarm` 进程当成已绑定桌面会话、自动降级为隐藏 CLI、直写原生历史或用 Codex 自产文件冒充 WorkBuddy 成果。已打包的 v0.2.0 尚未包含兼容性修复，本轮没有上传 GitHub。

## 判定依据

目标是由 Codex 指挥用户本机 WorkBuddy 桌面端制作视频，收回执行反馈，要求返工，再检查成果。2026-10-07 的实际执行记录没有足够证据证明这个闭环完成。已经存在的视频文件不能作为桥接成功的证据。

核查执行记录可确认：

1. 最初 MCP 健康检查返回 `online: false`、`status: offline`，提示没有活跃 interactive 会话；第一次视频派工返回 `state: blocked`。
2. 后续改为独立 CLI/隐藏 Gateway 和手工 ACP 调用。执行过程中出现本机 `ECONNREFUSED`、预热进程退出以及流中断。请求返回 `202 accepted` 只证明接收入口接受了请求，没有提供制作完成证据。
3. 事后核查发现交付成片的 Remotion 渲染进程属于 Codex 侧，代码编写、复制与打包也存在 Codex 侧执行。因此这批成片应归属 Codex 侧，不能宣称是 WorkBuddy 完成的制作结果。

以上来自实际执行输出与事后归属核查。文档不包含用户日志原文、会话标识、个人目录或素材内容。

## 桥接器的技术缺口

| 缺口 | v0.1.0 行为及后果 | 改进方向 |
| --- | --- | --- |
| 后端与桌面对话不一致 | `gateway` 可运行隐藏 Host，不能证明任务进入指定可见对话 | 个人路线明确使用 `desktop-acp`，派工保存并绑定会话 |
| 返工可能漂移 | 会话不匹配时改选最新会话 | 原会话失效时阻塞，不把返工发进别的对话 |
| 长任务消息不可观察 | 主要在结束后返回文本；兼容 Gateway 用 `response.text()` 等流结束 | 增量保存执行事件与状态，提供有界等待 |
| 运行记录在内存中 | MCP 进程结束会丢失 ACP/Gateway 执行映射 | 独立 worker 持续写入本地记录，重启后读取既有记录 |
| 默认超时偏短 | 桌面 ACP 默认约五分钟，兼容 Gateway 监听时间也与制作任务不一致 | 将任务超时与短 HTTP 请求超时分开，任务默认 30 分钟 |
| 空结果被当成完成 | 无文本输出会生成 `TASK_STATUS: completed` | 空结果、流中断、等待输入必须准确报告 |
| 验收只记一句说明 | 保存通过状态不证明文件存在或制作归属 | 验收需文件证据和实际检查说明 |
| 发包方式与安装提示不符 | 公开仓库根目录只有 README 与 ZIP；克隆后缺少 `package.json` | 明确先解压完整项目，版本按包内信息核对 |

## 工作流约束

连接失败应先修复通道，或者明确交给用户处理。Codex 不得通过自己制作相同视频来替代 WorkBuddy 派工，再把成果归属于 WorkBuddy。

模型名称写在提示词里不等于已经切换模型；Skill 名称出现在回复里不等于已经调用 Skill。应检查会话模型配置、WorkBuddy 执行事件和实际产物，分别记录已证实与未证实的部分。

改进代码、通过测试和健康检查属于工程验证。指定 WorkBuddy 会话的可见任务、连续返工及真实视频产物，按 [用户验收步骤](USER_ACCEPTANCE.md) 由用户最后验证；在完成前不宣称全链路已跑通。

## v0.3.0 队列修正

已改为 `desktop-queue`：在真实桌面 WorkBuddy 对话首次启动本机 helper，由桌面模型领取任务、使用自己的工具执行、主动回报并继续领取返工。Gateway 不启动另一个模型，不需要企业开放平台资质，也不通过改写原生数据库伪造会话。

队列的领取、身份校验、回报、同一会话返工、取消和超时已有自动化测试。Mac 解锁后已完成原生 helper 领取、小清单创建、同一会话自动领取一次返工、Edit 修改和独立文件验收。此前 ACP 失败记录保留；不能据此称为已经修复全部场景。以 QUEUE_WORKER.md 的最新实机记录为准。原 desktop-acp 作为兼容实现保留，不能再把打开桌面会话直接等同于存在 HTTP ACP endpoint。
